# Reconciliation rules

1. Verify the RPC `eth_chainId` against configuration before scanning. A mismatch exits 2 and does not produce a successful report. Ledger records for another chain or token receive identity findings and cannot match the configured asset.
2. Pin the latest header number/hash. Resolve `latest` discovery upper bound once. Reject future bounds, reversed bounds and ranges beyond `max_blocks`.
3. Discover configured-token Transfer logs to registered recipients in inclusive bounded chunks. Each returned event must match its separate successful receipt. Record completed and failed ranges; failed chunks make coverage and the run incomplete.
4. Deduplicate referenced/discovered transaction receipt requests. Require requested receipt hash, successful status, valid inclusion metadata and canonical block hash at that height. Receipt/log block, transaction and index metadata must agree. Strict Transfer decoding requires the signature, exactly three topics, zero address padding and exactly 32 data bytes. Malformed receipt Transfer evidence cannot establish deposits.
5. Event identity is chain ID + transaction hash + RPC block-global log index. Asset identity is chain ID + configured contract, never symbol or decimals. If an explicit log index is provided, select only that index. Otherwise prefer exact recipient+amount candidates, then recipient candidates, then amount candidates, then all configured-token candidates. Each step returns all candidates at that tier; verification requires exactly one. This fallback permits a unique event to explain a mismatch, never to conceal it.
6. Compare ledger and observed recipients against independently registered ownership, as well as each other. Compare normalized exact base-unit amounts. Mint events are excluded unless explicitly enabled. Zero-valued events are decoded but cannot satisfy a positive ledger amount.
7. Only successful canonical positive inbound events meeting policy are eligible. Confirmations equal `reference_head - inclusion_height + 1`. Under-confirmed credited events get a discrepancy; expected events get an investigation. This is not Ethereum consensus finality.
8. For credited records, compare optional ledger `credited_at_block` with inclusion and policy. A pre-inclusion height yields both inconsistent-height and premature-credit findings. A future claimed credit height is unresolved. Missing timing yields informational `HISTORICAL_CONFIRMATION_UNKNOWN`; current eligibility can still verify. A historical premature-credit conclusion is explicitly based on ledger-supplied timing.
9. Collect all selected credited claims per event. More than one is `DUPLICATE_CREDIT`, and none of those entries counts as verified. Valid unique current credits consume events even if their historical timing is discrepant, so historical issues do not manufacture unrecorded inbound deposits.
10. A uniquely matched eligible expected entry yields `ELIGIBLE_DEPOSIT_NOT_CREDITED`. In the reverse direction, each eligible in-range event without a valid associated ledger credit/expected association yields `UNRECORDED_ONCHAIN_TRANSFER`. Invalid amount/account claims do not consume deposits. These are investigation candidates, not assertions that unsolicited transfers are invoice payments.
11. Entries without transaction identity expose bounded-scan candidate event references but remain unresolved. No event is consumed on amount/address alone. Missing receipts are `not_observed`; provider/timeouts/header failures are unavailable, never proof of failure. Unobserved expected deposits are informational in severity but unresolved in verification state, and therefore exit 3.
12. Recheck every observed canonical header and the reference head. Replacement or unavailable anchors make the run incomplete. Normal head advancement does not invalidate the pinned snapshot. Persisted historical events are separately compared against canonical headers at their stored heights. Only a changed hash proves `REORG_OBSERVED`; absent receipts/headers do not. Recheck history headers too, and recheck the original head after historical comparison.

Finding order is stable by code, entry references and event references. Provider receipt arrival order does not determine output. Run IDs/timestamps vary; configuration and loaded snapshot fingerprints, reference chain view and deterministic findings support comparisons between runs.
