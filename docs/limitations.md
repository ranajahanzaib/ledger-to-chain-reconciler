# Limitations and operating assumptions

- One chain, one configured contract and one confirmation-count policy per run. No native ETH, ERC-721/1155, bridges, withdrawals or internal exchange trades.
- Standard ERC-20 event accounting only. Fee-on-transfer, rebasing, share accounting, unreliable Transfer events and custom deposit aggregators are excluded. Decimals/symbols never change raw event amounts.
- The RPC is trusted to return honest canonical headers, receipts and complete filter results. The program is not a light client, proof verifier or independent consensus node. A provider that silently omits logs can defeat discovery; using an independently operated node is an operational trust decision.
- Coverage is only the configured token, current ownership recipients and explicit inclusive block range. Referenced ledger receipts may be inspected outside that range, but reverse-discovery claims do not extend outside it. Partial scans are never clean. A head can reorg after the final check.
- Missing transaction identity stays unresolved even when amount/address candidates exist. Missing log indices require unique receipt attribution. Transaction success alone does not establish a deposit.
- Historical credit timing is supplied by the ledger, not recovered from chain history. Missing timing does not prevent a current match but cannot prove historical compliance. A current inclusion height may differ from past inclusion after a reorg.
- Address ownership must be supplied independently and is assumed valid for this audit. Ownership history, address reassignment, shared custodial addresses and customer allocation behind a shared address are unsupported. Reusing an address across distinct accounts is rejected; ownership across time needs an expanded model.
- Historical reorg detection requires the separate observation database and an obtainable replacement canonical header. A rollback below the old height leaves that old block unverifiable until replacement history is available. Missing receipts alone are never reorg proof. Without history, current noncanonical or recorded-block mismatches can be detected but not labelled proven historical reorgs.
- Source ledgers can change while an audit is running; the report preserves the data loaded by the adapters. CSV assumes the source producer writes atomically or provides an immutable snapshot. The SQLite adapter uses a read-only connection but does not lock application writes; provide a stable source snapshot for repeatable input. This tool does not lock application financial workflows.
- Evidence stays in memory during a bounded run. The caps target hundreds/thousands of entries, not adversarial full-chain indexing. HTTP response bodies (including decompressed content) are capped at 32 MiB before JSON decoding. Oversized/truncated results fail verification. Event-count limits still target reasonable audit workloads rather than full-chain indexing. Overall deadlines bound network work; CSV parsing is size/row bounded.
- History archives grow until the operator rotates them. SQLite and report writes are separate; a report failure may leave the run in history, exits 2, and requires an output retry. No automatic ledger correction, rollback or pruning occurs.
- Initial chain-ID/head failures and invalid discovery ranges are execution errors (2), rather than fabricated empty completed audits. Once evidence collection starts, unavailable receipt/chunk/header evidence is surfaced as incomplete (3).
- Local integration uses Foundry v1.4.4, Solidity 0.8.30 and actual `evm_snapshot`, `evm_revert`, `evm_setNextBlockTimestamp`, `anvil_mine` methods. Other local-node versions may differ. Public chain deployment is neither necessary nor tested. GitHub Actions is configured; a hosted CI run cannot be claimed until pushed and executed.
